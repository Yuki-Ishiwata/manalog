# ManaLog

石渡塾向け学習記録アプリの開発用プロジェクトです。PHP 8.2+ / MySQL 8.0互換を想定しています。

## 開発環境

1. `.env.example` を `.env` にコピーし、DB設定を入力します。
2. MySQLに `database/migrations/001_initial_schema.sql` から最新のマイグレーションまで番号順に適用します。既存DBはバックアップを取り、未適用のマイグレーションだけを追加します。
3. Webルートを `public/` に設定します（XAMPPでは `/manalog/public`）。
4. `composer install --no-dev` でWeb Pushライブラリを入れます。
5. 管理者ユーザーは初期セットアップ画面から作成します。

アップロード領域は公開ディレクトリ外の `storage/uploads/` を使います。Composerの `vendor/` も公開ディレクトリ外に置きます。

## 現在の実装

- PHPアプリの入口、環境設定読み込み、PDO接続
- 初回管理者作成、ログイン・ログアウト
- 管理者による生徒登録、一覧、無効化、パスワード再発行
- 生徒プロフィールの表示・編集
- 月〜土・8限までの時間割手入力・一括削除と今日の時間割表示
- 時間割画像の検証・一時保存・AI解析・確認後保存
- 月〜日の曜日別・帰宅後／夜の通知時刻とON/OFF、一時停止
- 夜の時刻は24:00〜29:59にも対応し、選んだ曜日の翌朝として保存
- PWAのインストール、Web Push購読・解除、cron送信、送信履歴
- 帰宅後と家庭学習の夜の振り返りを別々に保存・再開
- 従来の自由会話も引き続き利用可能
- 会話セッション・履歴の保存と表示、今日の教科を1つずつ各2問で聞く学習振り返り
- 教科名ごとの「質問しない教科」設定
- ブラウザ音声認識での文字起こし・自動送信・連続した会話モード、非対応時の手入力
- まなログ専用アカウントと塾DBアカウントの認証元別ログイン、塾生の初回連携
- 保護者専用ログインと複数の子どもの切替表示（AI会話全文は非表示）
- 講師向け生徒一覧、7日間の学習状況、塾の授業前サマリー
- 塾ごとのユーザー分離と、塾管理者／サービス運営者の権限区分
- 日付・科目別の学習記録一覧、理解度・要確認内容・問題正誤・写真の表示（生徒／保護者モード）
- 生徒プロフィール、時間割、チャット、通知設定を含む初期DBスキーマ
- モバイル向けのログイン画面

チャットと画像解析を使うには `.env` に `AI_API_KEY` と利用する `AI_MODEL` を設定してください。チャットではJPEG・PNG・WebPを1回4枚、1枚8MBまで添付できます。元画像は `storage/uploads/learning/` に非公開保存し、EXIF向きを補正した縮小画像をResponses APIへ送ります。同じ生徒が同じ写真を再送した場合は保存済み解析を再利用します。問題ページ上の○△×を記録し、後日ノートを送った場合は候補問題をAIとサーバー側で照合し、一致が明確なものだけ正誤を更新します。APIキーはサーバー側だけで使います。

## エックスサーバーへの配置

塾生認証には、まなログDB設定とは別に `SCHOOL_DB_HOST`、`SCHOOL_DB_PORT`、`SCHOOL_DB_NAME`、`SCHOOL_DB_USER`、`SCHOOL_DB_PASSWORD` を `.env` に設定します。`SCHOOL_DB_USER` は `kaiin`、`kaiin_syubetsu`、`syubetsu` の必要列だけを読める専用ユーザーにしてください。接続先DB名はサーバーの実際の塾DB名を指定します（ローカルでは `yoyaku` でした）。まなログ専用ユーザーは引き続き `DB_*` で認証します。

未登録IDは、まなログに同じログインIDがない場合に塾DBで認証し、初回成功時に `users.id` と塾の `kaiin.id` を連携します。認証失敗時に別DBへ切り替えて試しません。IDが衝突する塾生は `school:` を付けたログインIDを使います。退会・利用停止は `kaiin.delete_flg` と、期間内の「在籍」（`system_flg=1`、`zaiseki_flg=1`）で判定します。既存の塾DBや塾ログイン処理には書き込みません。

既存のまなログアカウントと塾生徒を結ぶ場合は、管理者画面の「既存アカウントを塾生徒に連携」で塾の `kaiin.id` を指定し、氏名・ログインIDを確認して確定します。名前による自動照合はしません。連携後はそのアカウントの認証先を塾DBへ切り替え、既存のパスワードハッシュはランダム値に置き換えます。ログイン試行はまなログ側でログインIDとIPのHMAC値を保存し、15分でIDあたり5回、IPあたり20回の失敗を制限します。`APP_KEY` には32文字以上のランダムな値を設定してください。

保護者向け表示には学習記録の一覧を表示します。日付・科目で絞り込みでき、学校授業／家庭学習・理解度・要確認内容・問題の正誤・関連写真を確認できます。本人の申告とAI推定は区別し、AIとの会話全文は表示しません。

`008_phase2_learning_records.sql` はPhase 2の保存領域を追加します。学習単元・日々の活動記録・理解度の時系列・質問と回答・問題の正誤・非公開写真と解析結果・チャットメッセージとの出典関係を保存できます。写真は生徒ごとのSHA-256で重複を検出し、同じ画像の解析結果を再利用できる構造です。完了した帰宅後・夜の振り返りは `learning_extraction_jobs` に入り、既存の `bin/send_notifications.php` cron が会話から記録を抽出します。抽出が失敗した場合は最大3回まで再試行します。`009_adaptive_review_checks.sql` は会話の進行段階を保存し、具体的な苦手内容が出たときだけAIの確認質問を追加します。確認質問と回答を学習記録に残し、回答内容に根拠がある場合だけAI推定の理解度を保存します。生徒・保護者モードの学習一覧はこの記録を日付・科目別に表示します。

`010_photo_chat_links.sql` は写真と投稿チャットを結びます。チャットで複数写真を送信でき、問題集の写真だけで問題と印を読み取る使い方と、問題集のあとにノート写真を送る使い方に対応します。ノートは直近30日以内の未判定問題だけを照合候補にし、問題番号とページ・教材または問題文が明確に一致しない場合は結びつけません。写真は本人のログインを確認するPHP経由でのみ表示します。

`011_weekly_review_sessions.sql` は週ごとの復習チャットを追加します。Phase 3では `016_weekend_review_proposals.sql` を適用すると、週末の提案を最大3件に絞り、未完了の項目を次週へ引き継ぎます。会話は提案数に応じて最大3回答で終了し、思い出せたか、ヒントが必要だったか、次回も復習が必要かを項目ごとに記録します。理解度の根拠は `learning_understanding_history` に追加されます。

`012_student_onboarding.sql` は新規生徒向け初回設定の進行状態を追加します。既存生徒は設定済みとして扱い、新しく登録された生徒は初回ログイン後に時間割、質問しない教科、曜日別通知時刻、ホーム画面追加・端末通知の順で設定します。通知の許可ダイアログは生徒がボタンを押したときだけ要求します。

`013_notification_resend.sql` は未回答の振り返り通知を1回再送する状態を記録します。通知の再送時刻は初回配信の60分後です。

`014_instructor_learning_summaries.sql` は講師向け学習サマリーのキャッシュ領域を追加します。学習記録の内容ハッシュが変わらない限り、AIサマリーを再利用します。サマリーはまなログ側で生成し、写真は有効な管理者・講師セッションと生徒所有者を照合する非公開URLからのみ表示します。塾DBの `kaiin.id` と授業日程は独立PDOで読み取り、塾DBには書き込みません。

`015_staff_parent_accounts.sql` は `teacher` と `parent` のロール、および保護者アカウントと生徒を結ぶ `parent_student_links` を追加します。管理者が講師・保護者のローカルアカウントを発行し、保護者に閲覧させる生徒を明示的に選びます。講師は学習サマリーのみ、保護者は紐付いた生徒の学習記録のみを閲覧できます。認証・権限判定はサーバー側で行い、塾DBには変更を加えません。

`016_weekend_review_proposals.sql` は土日の復習提案、提案項目ごとの実施状態・回答履歴・理解度履歴・Responses API使用量を保存します。週ごとに一度だけ提案を生成し、週内の新しい記録があれば復習会話開始前に更新します。生徒が会話を始めた後は提案を固定し、未完了・要再確認項目を最大6週引き継ぎます。生徒ホームにおすすめを表示し、保護者・講師画面にも現在週の提案と状態を表示します。週末通知は初期OFFで、曜日・時刻を生徒が設定します。通常通知の前後2時間に重なる場合は省略し、週ごとの一意キーで二重送信を防ぎます。`AI_INPUT_USD_PER_MILLION` と `AI_OUTPUT_USD_PER_MILLION` に使用モデルの単価を設定すると概算費用を記録します。空欄の場合もトークン数とモデルは記録し、推定費用はNULLです。

`017_tenant_dashboards.sql` は組織（塾）を作成し、既存ユーザーを石渡塾へ割り当てます。講師一覧・詳細、管理者のアカウント管理、保護者の子ども一覧と写真配信は、サーバー側で同じ塾のユーザーに限定します。保護者の親子リンクも同じ塾であることを検証します。管理者には `tenant` / `service` の範囲を保持し、塾管理者は自分の塾を管理します。ログインIDは現状グローバル一意のままです。別塾への本格提供時は、塾ごとのログイン入口と塾DBプロバイダー登録を追加してから運用を開始してください。

`deploy.sh` は `../i-yoyaku/deploy_ishiwata.sh` のSSH・rsync方式を参考にしています。初回の接続先と配置先は推測せず、`deploy.config.local` に設定します。

1. `deploy.config.example` を `deploy.config.local` にコピーし、SSH接続先、公開領域外の `DEPLOY_ROOT`、サブドメインのドキュメントルート `DEPLOY_PUBLIC_ROOT`、サーバー側の `DEPLOY_ENV_FILE` を入力します。
2. エックスサーバーのサブドメイン設定で `DEPLOY_PUBLIC_ROOT` を公開先として選びます。たとえば `.../public_html/manalog/` です。
3. サーバーに `DEPLOY_ENV_FILE` で指定した `.env` を作成します。別の場所に置いた場合、デプロイ時に `DEPLOY_ROOT/.env` へシンボリックリンクを作成します。このファイルと画像・ログはデプロイで転送しません。
4. `./deploy.sh --dry-run` で転送予定を確認し、`./deploy.sh --apply` で転送します。初回で `DEPLOY_ROOT` がまだない場合も、dry-run は作成予定と転送ファイルを表示します。
5. SQLマイグレーションは内容を確認し、専用DBに別途適用します。スクリプトはDBを変更しません。

`public/` の中身は `DEPLOY_PUBLIC_ROOT` に、`src/` と `database/migrations/` は `DEPLOY_ROOT` に転送します。`app_root.local.php` はサーバー上に生成し、公開側からアプリ本体を参照します。既存サイトや別DBには触れません。古いリモートファイルを自動削除しないため、不要ファイルが出た場合は個別に確認して削除してください。

## Phase 1.5 Web Push 導入

Web PushにはHTTPS、Service Worker、端末ごとの購読、VAPID鍵が必要です。iPhoneはホーム画面に追加したWebアプリから通知許可を操作します。AndroidはChromeなどの対応ブラウザからホーム画面に追加して使います。許可ダイアログは生徒が「この端末で通知を受け取る」を押したときだけ表示します。

1. DBをバックアップし、`database/migrations/006_web_push.sql` を **Manalog専用DB** に適用します。既存の曜日別時刻は残り、ONが初期値です。購読するまでは送信されません。
2. `composer install --no-dev --prefer-dist --optimize-autoloader` を実行します。`deploy.sh` は `vendor/`、`composer.json`、`composer.lock`、`bin/` を公開ディレクトリ外の `DEPLOY_ROOT` に転送します。
3. `./deploy.sh --dry-run` を確認してから `./deploy.sh --apply` で配置します。`public/` 以外に置く `.env`、`vendor/`、`bin/` はWebから直接参照できません。
4. サーバーの公開ディレクトリ外のアプリルートで `/usr/bin/php8.3 bin/generate_vapid.php https://manalog.ishiwata-juku.com/` を1回実行します。公開鍵・秘密鍵・subjectを **`DEPLOY_ENV_FILE` の `.env` だけ** に書き、秘密鍵は画面に表示しません。鍵を変えると既存の購読が無効になるため保管してください。`APP_BASE_URL=https://manalog.ishiwata-juku.com/` も `.env` に設定します。
5. エックスサーバーのcronに5分間隔で次を登録します。例: `*/5 * * * *`、実行コマンド `/usr/bin/php8.3 /home/xs934178/ishiwata-juku.com/manalog/bin/send_notifications.php >> /home/xs934178/ishiwata-juku.com/manalog/storage/logs/notification-cron.log 2>&1`。CLIのPHPに `curl`、`mbstring`、`openssl` が必要です。cronは `Asia/Tokyo` を明示して実行します。
6. iPhoneはSafariの共有メニューからホーム画面に追加し、そのアイコンからログインして通知を許可します。Androidはホーム画面に追加して通知を許可します。生徒画面で曜日別時刻・ON/OFF・一時停止を保存してください。

夜の `25:00` は選択した曜日の翌日 `01:00` として計算します。cronは予定時刻を過ぎてから12時間以内の未処理通知を拾うため、5分間隔から多少遅れても送信できます。同じ生徒・学習日・通知種別はDBで一意にし、端末ごとの送信結果を別に保存します。送信が受理された端末には再送しません。結果が不明な通信エラーも二重送信を避けるため自動再送しません。通知タップは対象の会話を開き、未回答の質問はそのまま残ります。管理者画面の「通知送信履歴」と `notification_deliveries` / `notification_delivery_devices` で結果とエラーを確認できます。

## Telegram 学習サマリー通知

生徒が帰宅後・夜の振り返りを完了すると、既存cronが会話から学習記録を抽出した後に、科目・単元・学習内容・学習時間・次に確認する内容をTelegramへ送信できます。通知は5分cronで処理し、Telegram側の一時エラーは最大5回まで再試行します。通知本文は構造化された学習記録から作成し、AIとの会話全文・写真は送信しません。

1. TelegramでBotFatherから通知用Botを作成し、Bot Tokenを取得します。通知先のTelegramアカウントまたはグループからBotを開始し、送信先のChat IDを確認します。
2. サーバーの公開領域外にある `.env` に `TELEGRAM_BOT_TOKEN` と `TELEGRAM_CHAT_ID` を設定します。トークンはソースコードやGitに登録しないでください。
3. `database/migrations/021_telegram_learning_summaries.sql` をまなログ専用DBに適用します。
4. `bin/send_notifications.php` のcronを5分ごとに実行します。Telegram設定がない場合は送信キューを作らず、既存のチャット動作にも影響しません。

通知ジョブは学習記録抽出と同じDBトランザクションで登録し、同じ振り返りセッションから重複通知しないようにしています。Telegramの停止時も生徒のチャット送信は待たされません。

ローカルの自動確認は `php tests/phase15.php` です。Manalog専用のローカルDBへ `006` を適用した後に実行してください。一時的なテスト生徒を作成し、終了時に削除します。実機ではiPhoneとAndroidそれぞれで購読、通知受信、タップで会話を開く動作、解除と一時停止を確認してください。

Phase 4は `017_tenant_dashboards.sql` 適用後に `php tests/phase4_dashboard_scope.php`、`php tests/phase4_dashboard_render.php admin`、`php tests/phase4_dashboard_render.php teacher`、`php tests/phase4_dashboard_render.php parent` を実行します。テナント検証はトランザクションをロールバックし、画面テストも一時データを残しません。週末復習の回帰確認は `php tests/phase3_weekly_review.php` です。
